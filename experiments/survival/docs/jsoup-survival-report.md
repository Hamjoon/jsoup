# Do LLM-generated unit tests survive library evolution? jsoup, 2017 to 2026

## Question

When a unit test is written against one release of a library, does it still pass, unmodified, at later releases? We compare the library's own developer tests with tests generated by an LLM using the five prompting techniques of Ouédraogo et al. (EMSE 31:103, 2026), over nine years of jsoup releases.

## Setup

- **Subject.** jsoup, a Java HTML parser. It uses the same language and test framework as the paper, so the replicated pipeline applies without change; it has 26 releases without a gap from 1.11.2 (2017-11, release *t*) to 1.23.2 (2026-08); and it has no runtime dependencies, so every release builds in one environment.
- **Developer tests.** The whole test suite at *t* (31 test classes; the network-dependent `integration` package excluded), 594 test methods passing at *t*.
- **LLM tests.** All 52 production classes of *t*, each given whole to the model with each of the five prompts (ZSL, FSL, CoT, ToT, GToT), one generation per class and prompt (the paper generated 30). Model `gpt-oss-120b`, temperature 0.7. The paper's 4,096-token input and output limits were not applied; they were constraints of the 2023 models. Generated files were extracted and compiled without any edit. Of 260 files, 131 compiled at *t*; after removing duplicate method bodies, 1,862 methods passed at *t*.
- **Survival.** A test counts as passing at *t* only if it passed in three runs. The test sources are frozen at *t* and recompiled and run against each later release. A test *survives* at release *R* if it passed at every release from *t* to *R*, so the denominator is fixed and survival only decreases. A test that did not survive is classified by its state at the first release where it stopped passing: compile failure (whole file), assertion failure, runtime exception, timeout, or class removed (the class under test no longer exists at that release).

## Observations

1. **After nine years, fewer LLM tests survive than developer tests: 23.1% against 31.5%.** LLM tests survive better for the first two years (1.14.3: 61.7% against 56.2%) and fall behind from 1.20.1; CoT is the only prompt that ends at the developer level (30.7%), and FSL ends lowest (19.9%).
2. **LLM tests break at changes to the tested class's own constructors and methods; developer tests break mostly when a class disappears.** Compile failures not caused by a removed class are 17.3% of developer tests and 46.9% of LLM tests, concentrated at 1.13.1 (node constructors lost their `baseUri` parameter: 387 methods), 1.15.1 (`Whitelist` renamed, `TokenQueue` methods removed: 166) and 1.18.1 (an inner class of `StructuralEvaluator` removed: 68), while 270 of the 373 developer compile failures name one of the six classes that were moved, renamed or removed.
3. **Neither the file-level compile rule nor the sample sizes explain the order.** Counting only methods whose own body contains a compile error (others treated as surviving) gives 80.6% for developer and 62.3% for LLM tests at 1.23.2; random subsets of 594 LLM tests survive 23.2% on average over 100 draws.

## Limitations

- One generation per class and prompt with one model; the paper used 30 generations. Twelve of the 52 classes (parser internals and `Selector`, `Node`) produced no compilable test, so the LLM denominator is weighted toward self-contained utility classes while the developer suite is weighted toward the parser and `Element`.
- Three rules are ours, not the paper's: the three-run pass requirement at *t*, no token limits, and the extractor's non-Java check applied only outside string literals (jsoup tests contain HTML strings).
- "Class removed" is judged by the class file for LLM tests and by the compiler's missing symbol for developer tests; the two rules describe the same events but were not applied identically.
